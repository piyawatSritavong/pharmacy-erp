# Roadmap V2–V6 แบ่งเป็น Phase

ข้อเสนอ ณ 2026-09-16 จาก [V1 baseline](V1_BASELINE.md) และ [เป้าหมาย T01–T29](GAP_MATRIX.md) ขณะจัดทำ roadmap ยังไม่มีงานใน roadmap นี้ถูกนับว่า implement แล้ว สถานะพัฒนาภายหลังดู [V2 execution record](v2-execution/README.md) และ [V2 acceptance checklist](V2_ACCEPTANCE_CHECKLIST.md)

## หลักการจัดลำดับ

พัฒนาสต๊อก หน่วยขาย ลูกค้า เอกสารการเงิน และคำสั่งซื้อเป็นแกนร่วมก่อนเพิ่มช่องทางขาย ใช้ Go backend และ PostgreSQL ชุดเดิมต่อ โดยแบ่งขอบเขตโมดูลให้ชัด ยังไม่มีเหตุผลจากการสำรวจนี้ที่จะต้องเขียนระบบใหม่หรือแยกทุกส่วนเป็น microservices

ลำดับที่สำคัญคือ **ข้อมูลสินค้า/หน่วย/ต้นทุน → ลูกค้า/เครดิต → sales order/จองสต๊อก → fulfillment/payment → เชื่อมช่องทาง → analytics → AI** บางงาน เช่น เก็บความต้องการ ออกแบบหน้าเว็บ ขอสิทธิ์ API และทดลองโมเดลด้วยข้อมูลจำลอง เริ่มล่วงหน้าได้ แต่การเปิดใช้งานจริงต้องผ่าน dependency ก่อน

กฎโปรโมชั่นทำที่ backend ร่วมกันทุกช่องทาง โดยลำดับราคาแนะนำคือ ราคาสัญญาลูกค้า → ราคาส่งตามจำนวน → ราคาสาขา/หน่วย → ราคาฐาน แล้วจึงประเมินโปรโมชั่นและส่วนลดตามนโยบายที่อนุมัติ ต้องตกลงกฎเมื่อราคา/โปรซ้อนกันก่อนลงมือ ไม่เปิดทางให้แต่ละ frontend คำนวณราคาเอง

## V2 — สต๊อกที่เชื่อถือได้ และการขายปลีก/ส่งพร้อมการเงิน

**ผลลัพธ์:** ใช้ฐาน V1 ต่อ แต่หน่วย ล็อต ต้นทุน และยอดรับ/จ่ายตรวจสอบได้ พร้อมเครดิตเทอม เช็ค และใบลดหนี้ ขั้นนี้เป็นฐานให้เซลล์และออนไลน์ ไม่ต้องรอเว็บจึงค่อยแก้สต๊อก

### V2-P0 · ยืนยันฐานและแก้ช่องว่างสำคัญ · 3–4 สัปดาห์

**งาน:** ทำ regression จากรายการเสี่ยงใน V1; แก้พักบิลให้เก็บหน่วย/ส่วนลดครบ; ใช้ cart contract ร่วมกับ remote; ทำ atomic remote checkout และ idempotency เพื่อให้ retry ไม่เกิดใบขายซ้ำ; ตรวจ retained/suppressed/reissued invoice ในยอดขายและรับเงินจริง; แยก original transaction กับ correction โดยคงหลักฐานเดิมไว้

จัดระบบ CI และ DB ทดสอบแยก, ตรวจ session revocation/สิทธิ์, ตรวจไม่ให้ credentials หลุดไป audit/log, ทดลอง backup+restore ทั้ง DB และรูป, ยืนยัน deployment config กับสภาพแวดล้อมจริง รวมรอบเปิด/ปิดเงินสดและยอดนับเทียบยอดระบบขั้นต่ำเพื่อกระทบยอดหน้าร้าน

**จบเมื่อ:** ขาย/พัก/เรียกกลับหน่วยกล่องพร้อมส่วนลดได้ตรงกัน; สองคำขอ checkout เดียวกันสร้างใบขายและตัดสต๊อกครั้งเดียว; test branch scope ผ่าน; restore แล้วเชื่อมเอกสารและล็อตกลับได้; ยอดเงินรับต้นฉบับและรายการปรับปรุงตามกลับได้ทุกบาทในชุด UAT ที่กำหนด

### V2-P1 · หน่วย ล็อต FEFO ต้นทุนและการจอง · 4–6 สัปดาห์

**งาน:** ขยายหน่วยร่วมให้ซื้อ/ขาย/โอน/คืนอยู่บนหน่วยฐานเดียว เก็บ conversion snapshot และรองรับการแตกแพ็กที่ธุรกิจใช้จริง; auto FEFO ข้ามล็อตในขายปกติพร้อมสิทธิ์ override; quarantine, recall และ write-off แบบระบุล็อต; รับ expiry/cost ของสินค้าทดแทนจากเคลม

สร้าง reservation ledger ที่มีเวลาหมดอายุและ atomic reserve/release/consume; แยก on-hand, sellable, reserved, expired/quarantine และ in-transit โดยไม่หักจำนวนเดียวกันซ้ำ ใช้กับทุก writer ไม่ใช่เฉพาะหน้าออนไลน์ เพิ่มรอบตรวจนับและรายงานเทียบ inventory/lot/movement/reservation

ตกลง FIFO หรือ Moving Average เป็นวิธีตีราคาสินค้าคงเหลือ **แยกจาก FEFO ซึ่งเป็นกฎเลือกล็อตจ่าย**; เก็บต้นทุนล็อตและ allocation ที่ตรวจสอบได้; กระจายส่วนลดซื้อ/ค่าส่งเข้าต้นทุนตามกฎเดียว และบันทึกผลการคืน/แก้ PO เป็น adjustment ที่ตามกลับได้

เพิ่ม job runner + event outbox พื้นฐาน, expiry bands 3/6/9 **เดือนปฏิทิน** และหน้ารับทราบ/มอบหมาย, รายงานมูลค่าเสี่ยงกับมูลค่าตัดจำหน่ายจริงแยกกัน การส่งภายนอกมาต่อใน V3-P3

**จบเมื่อ:** รับ 2 กล่อง กล่องละ 10 แล้วขาย 3 ชิ้นและโอน 1 กล่อง เหลือ 7 ชิ้นที่ต้นทาง; ขายข้ามสองล็อตตัดล็อตหมดอายุก่อนและกัน expired/quarantine; จองพร้อมขายไม่ oversell; release ซ้ำไม่เพิ่มของ; write-off กระทบยอด/ต้นทุนตรง ledger; alerts ที่ขอบเดือนทำงานและไม่แจ้งซ้ำ

### V2-P2 · ขายส่ง เครดิต เช็ค และใบลดหนี้ · 5–8 สัปดาห์

**งาน:** เพิ่ม customer master ขั้นต้นสำหรับบุคคล/องค์กร ที่อยู่ส่ง/ออกเอกสาร และ customer ID; เปิดเส้นทางเอกสาร quotation/invoice ที่จะใช้งานจริงหลังตัดสินใจเรื่อง Pro; price list/quantity break/customer contract; นโยบายโปรโมชั่นรายสาขาและวงเงินส่วนลด/ผู้อนุมัติ

เพิ่มลูกหนี้และเจ้าหนี้: เงื่อนไขเครดิต/วงเงิน/วันครบกำหนด, รับ/จ่ายเต็มหรือบางส่วน, allocation หลายเอกสาร, aging/statement; สถานะเช็ครับ/จ่าย/นำฝาก/ผ่าน/ตีกลับและการย้อนผล settlement; ใบลดหนี้อ้างใบเดิมทั้งขายและซื้อ, คืนบางส่วน, เครดิตคงเหลือ/คืนเงิน พร้อมแยกผลทางการเงินกับการรับสินค้าคืน

ทบทวนเอกสาร รพ.สต. และ summary/export อย. ที่มีโค้ดเดิม ตรวจหน่วยฐาน ชนิด movement และข้อมูลบริษัทกับผู้รับผิดชอบก่อนเปิดหน้าจอ; ไม่รวมสร้างการยื่นอิเล็กทรอนิกส์เข้าหน่วยงานโดยยังไม่ทราบข้อกำหนด

**จบเมื่อ:** ขายเครดิต 30 วันแล้วรับบางส่วนแสดงยอดค้างและ aging ถูกต้อง; เช็คยังไม่ผ่านไม่นับเป็นเงินรับเสร็จตามนโยบายที่ตกลง; เช็คตีกลับคืนหนี้ได้โดยไม่ซ้ำ; ใบลดหนี้ไม่เกินสิทธิ์คืนของเอกสารเดิม; คืนสินค้าและคืนเงินอย่างใดอย่างหนึ่งไม่ทำอีกอย่างโดยอัตโนมัติ; แต่ละสาขาจัดโปรได้ตาม policy

**ไม่รวมใน V2:** GL/บัญชีแยกประเภทเต็มรูปแบบ เงินเดือน สินทรัพย์ถาวร หรือระบบผ่อนชำระใหม่ สิ่งเหล่านี้ไม่ได้เป็นเงื่อนไขของเป้าหมายเครดิตเทอม และจะเพิ่มเมื่อมีขอบเขตธุรกิจเฉพาะ

## V3 — ลูกค้า สมาชิก และเซลล์ภาคสนาม

**ผลลัพธ์:** ลูกค้าคนเดียวมีประวัติข้ามสาขาได้ เซลล์รับออเดอร์และจัดของจากสาขา พร้อมซื้อซ้ำ/สะสมคะแนนโดยไม่ต้องรอ AI

### V3-P1 · CRM และ Loyalty ที่หน้าร้าน · 3–4 สัปดาห์

ต่อ customer master จาก V2 ให้มีสมัครสมาชิก/ค้นหา/รวมข้อมูลซ้ำอย่างตรวจสอบได้; points ledger แยก earn/redeem/expire/reverse; reward rules และคืนคะแนนเมื่อ refund; tag/segment ที่มีแหล่งข้อมูลชัดเจน; ความยินยอมแยกวัตถุประสงค์และช่องทาง, จำกัดผู้เห็นข้อมูลสุขภาพหรือความต้องการส่วนบุคคล

**จบเมื่อ:** ซื้อคนละสาขาเข้า member เดียวกันด้วยการยืนยันตัวตน; คืนบางส่วนย้อนคะแนนถูกต้อง; ไม่สร้างคะแนนซ้ำเมื่อ event ซ้ำ; ผู้ไม่มีสิทธิ์ไม่เห็น segment ที่จำกัด; ไม่สร้างข้อสรุปว่าลูกค้ามีโรคจากรายการซื้อเพียงอย่างเดียว

### V3-P2 · Sales Rep → คำสั่งซื้อ → เตรียม/ส่งสินค้า · 4–6 สัปดาห์

เพิ่ม role และขอบเขตลูกค้า/พื้นที่สำหรับเซลล์, เขตการขาย/นัดพบ/บันทึก visit, เสนอราคาและติดตาม quotation → sales order; ใช้ price list/เครดิต/โปรร่วมกับ POS; แนะนำสาขาจ่ายของจากพื้นที่ ระยะส่ง ความพร้อมสินค้าและสิทธิ์สาขา โดยเซลล์ยืนยันต้นทางตามสิทธิ์ ไม่เลือกจากระยะทางอย่างเดียว

ผูก order กับ stock reservation จาก V2; สาขารับงานเตรียม/หยิบล็อต/แพ็ก; เลือกรับเอง ส่งโดยร้าน หรือจ้างขนส่ง; นัดหมาย ที่อยู่ ค่าส่ง และหลักฐานส่งมอบ; เชื่อม requisition/transfer หากต้องเติมข้ามสาขา เพิ่มยอดขายแยก POS กับ field sales และผู้รับผิดชอบ

**จบเมื่อ:** เซลล์เปิด order ลูกค้านครปฐม สาขาที่ได้รับมอบหมายเห็นงานเดียวกันและ stock ถูกจอง; ลูกค้ารับเอง/ร้านส่ง/ขนส่งมีสถานะครบ; เซลล์อีกเขตไม่เห็นข้อมูลเกินสิทธิ์; cancel หรือเครดิตไม่ผ่านคืน reservation; ส่งไม่ครบติดตามยอดค้างส่งได้

### V3-P3 · Refill และการแจ้งเตือนตามกฎ · 3–5 สัปดาห์

ลงทะเบียนรายการที่ต้องซื้อซ้ำและรอบเตือนที่ลูกค้ายืนยัน ใช้วันซื้อ/รอบใช้ที่กำหนด ไม่คำนวณการใช้ยาหรือปรับการรักษาเอง; notification service สำหรับ LINE/SMS, ผูกผู้รับกับสมาชิก, opt-out/quiet hours, retry/deduplicate/delivery log; ตั้งข้อความ expiry ถึงพนักงาน และรายงานตัวเลขตาม template ถึงเจ้าของได้ด้วย scheduler

**จบเมื่อ:** สมาชิกที่ยินยอมได้รับเตือนตามรอบ; ถอนความยินยอมแล้วหยุด job ที่ยังไม่ส่ง; คนไม่เป็นสมาชิกไม่ได้รับ refill; event ซ้ำไม่ส่งซ้ำ; พนักงานตรวจงานส่งล้มเหลวได้ การเชื่อมผู้ให้บริการและค่าใช้จ่ายต้องยืนยันกับบัญชีจริงก่อนเปิดส่ง

## V4 — เว็บ E-Commerce และ OMS

**ผลลัพธ์:** ลูกค้าสั่งผ่านเว็บของร้าน ชำระ เลือกส่ง/รับสาขา และพนักงานจัดงานจากจุดเดียว สต๊อกและคะแนนใช้ฐานเดียวกับ POS

### V4-P1 · Order/Inventory/Payment contracts กลาง · 3–4 สัปดาห์

ขยาย sales order จาก V3 เป็น OMS: channel, seller branch, fulfillment branch, customer, commercial status, payment status และ shipment status แยกกัน; order lines/snapshots/discount/cost/fees; กฎ reserve→confirm→pick→pack→dispatch→complete พร้อม cancel/partial fulfillment/return

ขยาย outbox และ background jobs ให้ retry ได้; event idempotency, reconciliation, dead-letter queue/หน้าตามงานค้าง; แยก public customer APIs ออกจาก internal Admin/POS APIs และกำหนดสิทธิ์อ่านเฉพาะ catalog ที่เผยแพร่ได้

**จบเมื่อ:** POS และ order แย่งสินค้าชิ้นสุดท้ายโดยไม่ขายเกิน; order ถูกยกเลิกระหว่างเตรียมของมีผลชัดเจน; event สลับลำดับ/ซ้ำไม่ลดสต๊อกซ้ำ; ทุก order ย้อนถึงต้นทางและผู้รับผิดชอบได้

### V4-P2 · เว็บร้านค้าและการหาลูกค้าพื้นฐาน · 5–8 สัปดาห์

หน้าเว็บ catalog/search/category/product, ราคาที่ใช้ร่วมกับ backend, account/สมาชิก/cart/checkout, ที่อยู่และติดตาม order; ใช้ loyalty/โปรโมชั่นร่วม; รองรับมือถือ รวม SEO/หน้า landing และ campaign source/UTM/คูปองตั้งแต่เปิดเว็บ เพื่อเริ่มวัดแหล่งลูกค้าได้ทันที

เพิ่มนโยบายเผยแพร่สินค้าและขั้นตอนให้ผู้รับผิดชอบตรวจสินค้าที่ต้องควบคุมก่อนเปิดขายจริง ขอบเขตการขาย/การสื่อสารของสินค้ายาให้เจ้าของและผู้รับผิดชอบยืนยันก่อน release; เอกสารนี้ไม่ได้กำหนดข้อสรุปทางกฎหมายแทนธุรกิจ

**จบเมื่อ:** ลูกค้าทดลองทำเส้นทางค้นหา→ซื้อ→ดูสถานะบนมือถือได้; ราคาหน้าเว็บกับ checkout ตรงกัน; สมาชิกใช้/ได้รับคะแนนโดยไม่ซ้ำ; พนักงาน POS ไม่ต้องจัดการออเดอร์ผ่านบัญชีลูกค้า; บันทึก campaign source ถึง order ได้

### V4-P3 · รับชำระ ส่งสินค้า และ Click & Collect · 4–6 สัปดาห์

เชื่อม payment provider ที่เลือกสำหรับ PromptPay QR/บัตร/E-Wallet, รองรับผ่าน POS เท่าที่อุปกรณ์และผู้ให้บริการรองรับ; payment intent/pending/paid/expired/refunded, ตรวจ callback/จำนวนเงิน/สกุลเงิน/ผู้รับ, webhook ซ้ำและ timeout; refund และ settlement reconciliation เชื่อมเอกสาร V2

Click & Collect ใช้ reservation ที่มีอายุ, เลือกสาขา, หน้าหยิบ/แพ็ก, แจ้งพร้อมรับ, ยืนยันผู้รับ, no-show/cancel/refund; การส่งรองรับค่าส่งและ tracking เชื่อม carrier ที่ตกลง เพิ่ม dashboard ช่องทางเว็บเทียบ POS/field sales พร้อมต้นทุน/ค่ารับชำระ/ส่งพื้นฐาน

**จบเมื่อ:** QR หมดอายุไม่ตัดยอด paid; callback ปลอมหรือยอดผิดไม่อนุมัติ; ชำระสำเร็จแต่หน้าลูกค้าขาดการเชื่อมต่อยังตาม order เดิมได้; รับสาขาแล้วตัด stock reservation ครั้งเดียว; refund ย้อนหนี้/คะแนน/สต๊อกตามเหตุจริง; ทดลองเงินจริงมูลค่าต่ำในบัญชีที่ได้รับอนุญาตก่อนเปิดใช้ทั่วไป

## V5 — Marketplace, แคมเปญ และกำไรทุกช่องทาง

**ผลลัพธ์:** OMS รับงานหลายช่องทางและเห็นกำไรหลังค่าธรรมเนียม/ส่ง/คืน ไม่ตัดสินธุรกิจจากยอดขายรวมอย่างเดียว

### V5-P1 · Shopee/Lazada และ API สำหรับแอป · 5–8 สัปดาห์

ตรวจสิทธิ์เชื่อมต่อและเงื่อนไขของบัญชีจริงล่วงหน้า แล้วทำ connector ทีละช่องทาง: product/SKU/unit mapping, token lifecycle, orders/cancel/refund, stock updates, shipment และ reconciliation; เริ่มแพลตฟอร์มหนึ่งให้จบวงจรก่อนเพิ่มอีกแพลตฟอร์ม ใช้ provider settings เดิมเป็นฐานข้อมูลประกอบ ไม่ถือเป็น adapter ที่ใช้ได้แล้ว

รวมงานเข้า OMS; เสนอเป้าหมาย stock update ภายใน 60 วินาทีในสภาวะปกติสำหรับ pilot และแสดง last synced/error แต่ต้องวัดและปรับตามข้อจำกัด API จริง สต๊อกภายในตัด/จองแบบ transaction ส่วนภายนอกเป็นการ sync ที่มีความหน่วง ต้องมี safety stock และช่องทางแก้ยอดผิด

เพิ่ม contract สำหรับแอปลูกค้าให้ใช้ customer/order/loyalty API เดียวกับเว็บ ทดสอบการเรียกผ่าน client อีกตัว; ไม่รวมสร้าง native iOS/Android เต็มแอปในเวลาประเมินนี้ การผูกสมาชิกจาก marketplace ต้องอาศัยตัวตนที่ยืนยันได้และข้อมูลที่แพลตฟอร์มให้ ห้ามจับคู่จากชื่ออย่างเดียว

**จบเมื่อ:** order ซ้ำเข้าครั้งเดียว, SKU/unit ผิดเข้า exception queue, token หมดอายุมีทางกู้คืน, webhook หายถูกเติมจาก reconciliation, POS/เว็บ/แอป/Marketplace ใช้ stock availability เดียวกัน, ยกเลิกและคืนสินค้าตามกลับได้

### V5-P2 · Campaign/O2O และการซื้อซ้ำ · 3–5 สัปดาห์

ต่อยอด campaign source จาก V4: landing/coupon/referral, segmentation ตาม consent, แคมเปญชวนกลับเว็บ/รับสาขา, ข้อเสนอระบายล็อตใกล้หมดอายุภายในนโยบายสินค้า, งบและประสิทธิผล; วัด conversion/repeat purchase/ต้นทุนหาลูกค้าจากข้อมูลที่มีหลักฐาน

**จบเมื่อ:** ตาม campaign→order→refund ได้, opt-out มีผลทุก job, คูปองใช้ซ้ำเกินสิทธิ์ไม่ได้, รายงานแยกยอดที่วัดที่มาได้กับยอดที่ไม่ทราบที่มา; การยิงโฆษณา/ส่งข้อความจริงใช้งบและการอนุมัติของเจ้าของแคมเปญ

### V5-P3 · ต้นทุนและกำไรครบช่องทาง · 4–7 สัปดาห์

รับ statement/settlement, GP/commission/payment fees/ค่าส่ง/subsidy/คืนเงิน/ต้นทุนแคมเปญ; ผูกกับ order และรอบเวลา, แยกยอดประมาณการกับยอดที่กระทบแล้ว; channel dashboard ตั้งแต่ gross sales→discount→refund→net sales→COGS→fees/shipping→contribution profit โดยยังไม่เรียกกำไรสุทธิทั้งบริษัทถ้ายังไม่มีค่าใช้จ่ายทั้งหมด

เพิ่ม expiry loss/trend/aging, การระบายก่อนหมดอายุ และรายงานเทียบต้นทุน/stock valuation/เงินจริง; กำหนด metric glossary ที่ AI V6 จะใช้ ลดการตีความชื่อยอดไม่ตรงกัน

**จบเมื่อ:** เลือก order จากทุกช่องทางแล้วตามรายได้/ต้นทุน/ค่าธรรมเนียม/เงินรับได้; ยอดที่ยังไม่ทราบ fee แสดง pending ไม่แสดงกำไรยืนยัน; expiry risk ไม่ถูกนับเป็น realized loss; คืนบางส่วนย้อน metrics ครบ

## V6 — AI ภายในองค์กรที่ทำงานตามสิทธิ์

**ผลลัพธ์:** ใช้ข้อมูลที่นิยามและตรวจสอบแล้วเพื่อตอบรายงานและช่วยงาน โดยธุรกรรมยังผ่าน service ที่ตรวจสิทธิ์และบันทึกหลักฐานเหมือนคนทำ

### V6-P1 · Local AI และแชทรายงานแบบอ่านอย่างเดียว · 3–4 สัปดาห์

ใช้ model inference, embeddings และดัชนีเอกสารภายในสภาพแวดล้อมที่ธุรกิจควบคุม; กำหนดเครือข่ายออก/telemetry/log/backup/retention อย่างชัดเจนและทดสอบการส่งข้อมูลออก ไม่ถือว่าแค่ติดตั้งโมเดล local แล้วบรรลุ privacy ทุกข้อ

เริ่ม read-only tools ที่มีพารามิเตอร์แน่นอน เช่น ยอดรายวัน สต๊อกพร้อมขาย expiry และกำไรช่องทาง; ใช้ metric glossary จาก V5; แสดงช่วงเวลา สาขา ข้อมูล ณ เวลา และลิงก์รายงาน/เอกสารประกอบ; ไม่ให้รัน SQL อิสระใน production

**จบเมื่อ:** ชุดคำถามภาษาไทยที่ตกลงร่วมกันให้ตัวเลขตรง deterministic report; คำถามกำกวมให้ถามต่อ; ไม่ทราบข้อมูลให้บอกไม่ทราบ; สิทธิ์ผลลัพธ์ไม่เกินผู้ถาม; คำสั่งในเอกสารที่ค้นพบไม่เปลี่ยนกฎระบบ; ทดสอบนโยบายไม่มี business data ถูกส่งไปฝึกโมเดลภายนอก

### V6-P2 · รายงาน LINE และผู้ช่วยกลุ่มพนักงาน · 3–5 สัปดาห์

ใช้ notification service V3 ส่งรายงานที่ AI ช่วยเรียบเรียงให้เจ้าของตามผู้รับ/เวลาที่อนุมัติ; พนักงานถามจากคู่มือสินค้า/วิธีทำงานที่รับรอง และ report tools ตามสิทธิ์กลุ่ม; แยกกลุ่มสาขาออกจากสิทธิ์เจ้าของ ไม่ผูกคำว่า “อยู่ในกลุ่ม” กับ Superadmin

**จบเมื่อ:** ตัวเลขในข้อความตรง report snapshot, อ้างอิงแหล่งข้อมูลได้, ไม่ส่งรายงานสาขาหรือข้อมูลลูกค้าเกินสิทธิ์, ปิด bot/หยุด schedule ได้ และมี delivery audit โดยไม่เก็บเนื้อหาลับเกินจำเป็น

**ขอบเขตข้อมูล:** “ไม่ส่งข้อมูลไปฝึกโมเดล” กับ “ข้อมูลไม่ออกนอกองค์กรเลย” เป็นคนละเงื่อนไข การส่งข้อความรายงานผ่าน LINE/SMS ทำให้เนื้อหานั้นออกไปยังผู้ให้บริการข้อความ หากต้องการไม่ออกเลย ให้ส่งเพียงข้อความแจ้งและลิงก์กลับหน้ารายงานภายใน พร้อมให้เจ้าของเลือกขอบเขตก่อนเปิดใช้งาน

### V6-P3 · AI ช่วยสร้างงานผ่านหน้าจอ Superadmin · 4–7 สัปดาห์

เริ่มจาก **สร้างร่างคำขอโอน** ไม่เริ่มจากมอบสิทธิ์ Superadmin ทั้งหมดให้ AI เครื่องมือเรียก service/API ที่มี business validation ร่วมกับหน้าจอเดิม และแสดงผลให้เจ้าของตรวจใน Superadmin ไม่ต้องจำลองการคลิกหน้าจอที่เปลี่ยนตามขนาดจอ

ตัวอย่างคำสั่ง “วิลแชร์ V-001 หมด โอนจากโกดังไปนครปฐม 5 ตัว”:

1. ระบุผู้สั่งและสิทธิ์, resolve SKU/ชื่อสินค้า/หน่วย/ต้นทาง/ปลายทาง; ถ้าไม่ชัดให้ถาม ไม่เดาสินค้าแทน
2. ตรวจของขายได้และ reservation, เลือกล็อตตาม FEFO; ถ้าของไม่พอแสดงจำนวนจริงและทางเลือก ไม่ทำ stock ติดลบ
3. สร้างข้อเสนอหรือ draft พร้อม 5 ตัว ต้นทาง/ปลายทาง ล็อต และผลกระทบ แล้วแสดงใน Superadmin
4. ผู้มีสิทธิ์อนุมัติข้อมูลชุดนั้น; backend ตรวจซ้ำว่าข้อมูลยังไม่เปลี่ยน ใช้ idempotency key แล้วสร้าง/ส่งงานตามขอบเขตที่อนุมัติ
5. สาขารับของจริงตามกระบวนการ V1/V3; AI ไม่ยืนยันการรับจริงแทนพนักงาน และรายงานเลขใบโอนกับสถานะที่ทำสำเร็จจริง

**จบเมื่อ:** retry ไม่สร้างใบโอนซ้ำ, ข้อมูลเปลี่ยนหลัง preview ต้องให้ทบทวน, stock/สิทธิ์ไม่พอถูกปฏิเสธ, ปลายทางต้องรับจริง, audit ผูก user→AI proposal→approval→document; มี kill switch และเปิด allowlist ทีละ action ไม่รวม hard delete, เปลี่ยนสิทธิ์, ปิดเดือน หรือแก้ยอดการเงินในรุ่นเริ่มต้น

งานอ่านอย่างเดียวที่ตอบผิดแก้คำตอบได้ แต่งาน mutation ต้องมี business authorization ทุกครั้งตาม policy ที่ตกลง อาจขยายเป็นอัตโนมัติบางกรณีภายหลังได้หลังมีผล pilot ไม่ถือว่าผู้ใช้แชททุกคนมีสิทธิ์สั่งระบบทั้งหมด

## ประมาณการและวิธีคำนวณ

เป็นกรอบวางแผนจากขนาดขอบเขต ไม่ใช่สัญญาส่งมอบหรือประมาณราคาที่ผ่าน discovery สมมติทีม developer 2 คนเต็มเวลา, QA 1 คน, UX ประมาณครึ่งเวลา และเจ้าของระบบ/ฝ่ายงานตอบเรื่องกฎและ UAT ได้ทุกสัปดาห์ ช่วงแต่ละ Phase รวมพัฒนา ทดสอบ และ pilot ของ Phase นั้นแล้ว

| Version | Phase รวม | เวลาฐานของทีม | Developer effort โดยประมาณ |
| --- | --- | --- | --- |
| V2 | 3–4 + 4–6 + 5–8 | 12–18 สัปดาห์ | 24–36 คน-สัปดาห์ |
| V3 | 3–4 + 4–6 + 3–5 | 10–15 สัปดาห์ | 20–30 คน-สัปดาห์ |
| V4 | 3–4 + 5–8 + 4–6 | 12–18 สัปดาห์ | 24–36 คน-สัปดาห์ |
| V5 | 5–8 + 3–5 + 4–7 | 12–20 สัปดาห์ | 24–40 คน-สัปดาห์ |
| V6 | 3–4 + 3–5 + 4–7 | 10–16 สัปดาห์ | 20–32 คน-สัปดาห์ |
| รวม | ทำตาม dependency | **56–87 สัปดาห์** | **112–174 คน-สัปดาห์** |

สำรองความไม่แน่นอนข้ามโมดูล/ข้อมูลเดิม 20%: `56–87 × 1.20 ≈ 67–104 สัปดาห์` หรือประมาณ **16–24 เดือน** สำหรับทีมสมมตินี้ ไม่รวมการรออนุมัติบัญชีภายนอกที่ยาวผิดปกติ native app เต็มรูปแบบ งานล้างข้อมูลจำนวนมาก และ GL/เงินเดือน ตัวเลขระยะไกล V5/V6 มีความมั่นใจต่ำกว่า V2 ต้องประเมินใหม่หลังแต่ละรุ่นด้วย throughput จริง

คำนวณงบพัฒนาเมื่อทราบค่าแรงได้จากคน-สัปดาห์ของแต่ละบทบาท × ต้นทุนจริงต่อสัปดาห์ แล้วเพิ่มค่า infrastructure, payment/message/API, โฆษณา และเครื่อง AI ตามขนาดใช้งาน ไม่ตั้งงบเงินบาทหรือสเปก GPU จากข้อมูลที่ยังไม่ทราบ

หากต้องการเปิดออนไลน์เร็ว ให้ทำ discovery/provider onboarding/UX เว็บควบคู่กับ V2 แต่ยังต้องผ่านหน่วย สต๊อกจอง ราคา order และการชำระก่อนเปิดขาย ห้ามย่นเวลาโดยข้ามการกัน oversell หรือรับเงินซ้ำ

## เกณฑ์ส่งมอบร่วมทุก Version

- มี feature IDs, migration/data backfill plan, rollback หรือ recovery plan, permissions และเอกสารการใช้ที่ตรง implementation
- ผ่าน unit/integration tests ที่จำเป็น, UAT โดยผู้ใช้จริง และเส้นทางสำคัญบนมือถือ/desktop; integration tests ใช้ DB แยกจากร้าน
- ตรวจยอดสินค้า/ล็อต/จอง/เอกสาร/รับจ่ายไม่คลาดหลัง create, edit, cancel, return, retry และ concurrent requests ที่อยู่ในขอบเขต
- ช่องทางภายนอกทดลองครบ success/failure/retry ด้วยบัญชีที่ได้รับอนุญาตก่อนถือว่า “เชื่อมแล้ว”
- บันทึก release commit, รุ่น schema ที่ใช้, ผลทดสอบ, ข้อจำกัด, ปัญหาคงค้าง และย้ายงานที่ไม่ผ่านไป Phase ชัดเจน ไม่ปิดงานด้วยภาพหน้าจออย่างเดียว
