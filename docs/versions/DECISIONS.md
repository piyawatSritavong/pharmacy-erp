# สมมติฐาน การตัดสินใจ และการบันทึกรุ่นถัดไป

2026-09-16 · [ดัชนี](README.md)

## เรื่องที่รับเป็นทิศทางแล้ว

- เก็บโค้ดปัจจุบันเป็น baseline V1 และพัฒนาสะสมต่อเป็น V2–V6 แบ่ง Phase โดยแต่ละรุ่นสืบทอดงานเดิมที่ยังใช้งานอยู่
- เป้าหมายใหม่ของเจ้าของโครงการรวมราคาปลีก/ส่ง บัตร/E-Wallet/เครดิต แม้เอกสารข้อเสนอเก่าเคยปฏิเสธราคาหลายระดับและบัตร ให้ใช้คำขอล่าสุดเป็นทิศทางของ roadmap ไม่ย้อนกลับไปยึดข้อปฏิเสธเก่า
- ใช้หน่วย โปรโมชั่น คลัง และเอกสารที่มีอยู่เป็นฐาน ไม่สร้างระบบราคา/สต๊อกอีกชุดแยกสำหรับเว็บไซต์หรือ AI
- แจ้ง refill และส่งรายงานแบบกำหนดกฎได้ตั้งแต่ V3 ไม่ต้องรอ AI จึงค่อยมีระบบแจ้งเตือน
- งานนี้บันทึกและวางแผน ไม่ได้เปิดฟีเจอร์ Pro, เปลี่ยนกฎการเงิน, ย้ายข้อมูลจริง หรือเชื่อมบัญชีภายนอก

## งานเดิมที่ยังไม่ครบ และงานที่ไม่ควรเผลอทำกลับมา

| รายการ | ที่จัดไว้ |
| --- | --- |
| เอกสารขาย/ใบเสนอราคา/รพ.สต. ที่ปิดหน้าจอ | V2-P2: เปิดวงจรที่ธุรกิจเลือกใช้และ UAT เอกสารจริง |
| อย. summary หลัง Pro gate | V2-P2: ตรวจข้อมูลสินค้า/ใบอนุญาต/หน่วยฐาน/ช่วงเวลาและ export กับผู้รับผิดชอบ; การยื่นอิเล็กทรอนิกส์จริงแยกประเมินหลังทราบช่องทาง |
| PO ปัจจุบันรับเข้าทันที ไม่มี approval/partial receipt | V2-P1 จัดข้อมูลหน่วย/ล็อตให้รองรับ; ถ้าร้านต้องแยกสั่งซื้อกับรับบางส่วนจริง ให้แตกงานย่อยก่อนจบ V2 และปรับประมาณการ |
| รายงานกำไรขั้นต้นที่ไม่อยู่เมนู | ตรวจสูตร/ยอดฐาน V2-P0/P1; จัดหน้ารายงานร่วมกับ V5-P3 ไม่เขียนซ้ำทั้งโมดูล |
| Marketplace scaffold/credentials | V2-P0 ตรวจการเก็บ secret และ audit; V5-P1 ทำ integration จริง |
| Backup, CI, device UAT และรูปสินค้า local ที่ยังไม่พร้อม | V2-P0 ต้องมีหลักฐานจริงก่อนเพิ่มภาระระบบ |
| Generate Report ที่ถูกถอด | ไม่คืนทุกอย่างอัตโนมัติ; V5 ทำ metric/report ที่ต้องใช้ และ V6 ใช้ read-only report tools; custom builder เป็น backlog แยกถ้าขอเพิ่ม |
| ระบบผ่อนชำระแบบเก่า | ไม่คืนอัตโนมัติ; เครดิตเทอมไม่เท่ากับผ่อนรายงวด ถ้าต้องการให้กำหนดสัญญา/ดอกเบี้ย/การรับชำระและแผนใหม่ |
| Pro subscription, SaaS หลาย tenant, เงินเดือน, GL เต็มชุด, native app, AI ซื้อ/จ่ายเงินเอง | นอกกรอบประมาณการ V2–V6 นี้; ไม่ใช่ฟีเจอร์ที่นับว่าเสร็จแล้วหรือถูกลืมไว้ |

## วิธีใช้เป็นบันทึกต่อเนื่อง

1. V1 baseline เก็บสิ่งที่พบ ณ commit เดิมไว้ ถ้าพบข้อผิดพลาดให้เพิ่ม correction พร้อมวันที่และหลักฐาน ห้ามแก้ให้ดูเหมือนฟีเจอร์ของ V2 มีมาตั้งแต่ V1
2. แต่ละงานใช้รหัส เช่น `V2-P1-001` ผูกกับเป้าหมาย `T13` และ baseline `V1-23` ระบุสิ่งที่ต้องรักษาและผลทดสอบ
3. สถานะงานใช้ `planned → in_progress → in_review → verified → released`; งานที่ถูกบล็อกระบุเหตุ/ผู้รับผิดชอบ; คำว่า released ต้องมี commit และการยอมรับงานจริง
4. ก่อนจบแต่ละ Version สร้าง `V2_RELEASE.md`, `V3_RELEASE.md` ตามลำดับ: บอกฟีเจอร์ใหม่ สิ่งที่เปลี่ยน/ถอด migration ผลทดสอบ ข้อจำกัด และงานยกไป Phase ไหน
5. อัปเดต roadmap/matrix และ decision log ตามผลจริง โดยเก็บเหตุผลการย้ายงาน ไม่ใช้เอกสารข้อเสนอแทนหลักฐาน release
6. ใช้ Git commit/tag หลังตรวจงานตามขั้นตอน repository; เอกสารชุดนี้ยังไม่ได้สร้าง release tag หรืออ้างว่า production อยู่ V1 ตาม database snapshot
